**규칙:** `order_settlement.py`에 `orders_xlsx`를 넘길 때, 같은 출고일(배치)에 대해 **여러 날짜의 발주발송 export 파일을 합쳐서(union) 넘기지 않는다.** `/Volumes/External/Downloads/스마트스토어_*발주발송관리_*.xlsx` 중 그 출고일에 해당하는 **가장 최신 파일 딱 1개만** 쓴다.

**Why:** 2026-07-23 정영은 호올스 캔디 COGS를 반영하면서 `--add-cogs`와 함께 7/22 export + 7/23 export 두 파일을 같이 넘겼다. 스크립트는 상품주문번호 union-dedup만 하지, 취소 여부는 모른다. 7/22 파일엔 아직 **취소되기 전의 이정희 주문**(룰루레몬 헤드밴드)이 남아있었고, 7/23 파일(취소 확정 후 export)에는 빠져 있었다 — 두 파일을 합치자 이정희 주문이 매출에 되살아나 매출이 ₩268,911→₩300,491로 잘못 부풀었다(수기 섹션엔 이미 "이정희 취소 확인" 메모가 있었는데도). 7/23 파일만 다시 넘겨서 바로잡았다.

**How to apply:**
- Naver의 발주발송 export는 **누적 스냅샷**이다 — 최신 파일 하나가 그 시점의 "현재 유효한 주문 전체"를 반영한다(취소된 건 최신 export엔 아예 안 나옴). 옛 파일 + 새 파일을 합쳐 쓰는 건 §20-4(신규 export의 dedup)와는 다른 상황 — §20-4는 "새 주문 인식"이 목적이라 여러 파일을 합쳐도 되지만, **매출 재계산(--add-cogs 재실행 등)** 목적이면 최신 파일 하나로 충분하고 더 안전하다.
- **"정산해!" 라이브 트리거로 반영할 때도 이 규칙 그대로 적용** — 무인 자동화(`settlement-auto-reconcile`)는 2026-07-24 사용자 지적으로 롤백됐지만(§20-15), 이 파일-선정 안전규칙 자체는 라이브 반영에도 유효하다.
- 취소 확인이 안 된 상태에서 옛 파일을 다시 쓸 일이 생기면, 먼저 그 출고일 md의 "취소 메모" 섹션을 확인해서 취소된 주문번호를 빼고 넘길 것.
